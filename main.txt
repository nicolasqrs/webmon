WEBMON - MODE D'EMPLOI ET INTERFACES WEB

MODE D'EMPLOI RAPIDE : AJOUTER UNE CIBLE

Prérequis : WebMon est démarré. Pour les commandes ci-dessous, ouvrir un
terminal sur le serveur WebMon et se placer dans le dossier du projet :
cd ~/webmon
(Adapter ce chemin si le projet est installé ailleurs.)

A. AJOUTER UN CONTENEUR

1. Lancer votre application avec sa commande docker run ou son propre Compose.
   Elle doit tourner sur le même moteur Docker que WebMon.
   Vérifier sa présence : docker ps -a

2. Attendre environ 30 à 60 secondes, puis actualiser :
   http://IP_DU_SERVEUR/
   WebMon découvre le conteneur automatiquement, sans formulaire d'ajout.

3. Ouvrir Grafana > Dashboards > WebMon > WebMon - Conteneurs.
   Choisir son nom dans le filtre Conteneur pour voir sa sonde et ses ressources.

4. Si le résultat est Non testé, configurer un healthcheck adapté à
   l'application. Démarré signifie que le processus tourne ; OK signifie
   que la sonde disponible réussit.

Pour un exemple de lancement et de healthcheck, lire plus bas
« AJOUTER UN CONTENEUR À WEBMON ».
Un conteneur sur une autre machine n'est pas découvert automatiquement.
Pour surveiller son service web, utiliser la procédure B avec son URL.

B. AJOUTER UN SITE WEB

1. Ouvrir le fichier de configuration :
   nano config/websites.json

2. Remplacer [] par la liste de vos sites (exemple complet plus bas).
   Pour ajouter un site à une liste existante, conserver les entrées actuelles
   et ajouter un objet séparé du précédent par une virgule.
   Ne pas ajouter de virgule après le dernier objet.
   Donner à chaque site un nom unique et son URL HTTP ou HTTPS complète.

3. Enregistrer avec Ctrl+O, Entrée, puis quitter avec Ctrl+X.
   Vérifier la syntaxe :
   docker exec webmon-monitor jq empty /website-config/websites.json

4. Attendre environ 30 à 60 secondes, puis ouvrir :
   Grafana > Dashboards > WebMon > WebMon - Sites web
   http://IP_DU_SERVEUR:3000/d/webmon-websites/webmon-sites-web

5. Choisir le site dans le filtre Site. Vérifier son état OK, son code HTTP
   et son temps de réponse. Une panne est confirmée après le nombre
   d'échecs consécutifs configuré.

Les URL sont relues automatiquement : aucun redémarrage n'est nécessaire
pour ajouter un site lorsque la fonctionnalité est déjà déployée.
Pour retirer un site, supprimer uniquement son objet de la liste JSON.
Pour les exemples, le déploiement et le dépannage, lire plus bas
« SUPERVISION DES SITES WEB NON CONTENEURISÉS ».

Remplacer IP_DU_SERVEUR par l'adresse du serveur WebMon.
Un site distant doit être accessible depuis le monitor.
Une URL localhost désigne le conteneur monitor ; pour un site hébergé
sur la machine Docker, utiliser host.docker.internal avec le bon port.


INTERFACES WEB

Depuis le serveur lui-même, utiliser les adresses localhost ci-dessous.
Depuis un autre ordinateur, remplacer localhost par l'adresse IP du serveur.
Exemple : http://IP_DU_SERVEUR:3000

INTERFACES PRINCIPALES

WebMon
Adresse : http://localhost/
Rôle : afficher les conteneurs Docker, leur état fonctionnel et les pannes détectées.

Grafana
Adresse : http://localhost:3000/
Rôle : consulter les tableaux de bord de métriques et les logs.
Identifiants initiaux configurés : admin / admin, sauf modification.
Les logs Loki se consultent dans Grafana, rubrique Explore, source Loki.

Dashboard simplifié des conteneurs :
http://localhost:3000/d/webmon-containers/webmon-conteneurs
Dans Grafana : Dashboards > WebMon > WebMon - Conteneurs.
Il affiche l'état Docker, la sonde (healthcheck, HTTP ou heartbeat),
les pannes confirmées, le CPU, la mémoire et le réseau.
La liste suit automatiquement les nouveaux conteneurs du même hôte Docker.
Un conteneur sans sonde applicative est affiché comme Non testé.
Guide : docs/CONTAINER_MONITORING.md

Prometheus
Adresse : http://localhost:9090/
Rôle : interroger les métriques et vérifier les cibles de collecte.
Cibles de supervision : http://localhost:9090/targets

cAdvisor
Adresse : http://localhost:8080/
Rôle : consulter les ressources utilisées par les conteneurs (CPU, mémoire, réseau).


ENDPOINTS TECHNIQUES

Ces adresses renvoient du JSON, des métriques ou un état de santé.
Elles ne sont pas des tableaux de bord.

API WebMon - Conteneurs
http://localhost/api/containers

API WebMon - Tâches
http://localhost/api/tasks

Loki - État de santé
http://localhost:3100/ready
Loki ne possède pas d'interface graphique autonome dans cette stack.

Node Exporter - Métriques du serveur
http://localhost:9100/metrics

PostgreSQL Exporter - Métriques de la base
http://localhost:9187/metrics

Le backend expose aussi /health et /metrics sur son port Docker interne 3001.
Ces deux routes ne sont pas publiées par le reverse proxy actuel.
Prometheus collecte directement les métriques du backend sur le réseau Docker.

PostgreSQL, Promtail, le monitor, la sonde et le worker de démonstration
ne disposent pas d'une interface utilisateur web publiée dans cette configuration.


DÉMONSTRATION ET DÉPANNAGE

Guide complet : docs/DEMO_DEPLOYMENT.md

Démarrer la stack de démonstration :
docker compose -f docker-compose.yml -f docker-compose.demo.yml up -d --build

Tester la panne et la reconstruction du worker de démonstration :
bash scripts/test-demo.sh

Après recréation du backend ou du frontend, si Nginx retourne 502 :
docker compose -f docker-compose.yml -f docker-compose.demo.yml restart nginx
Attendre quelques secondes avant de réessayer l'interface.

Les adresses et identifiants ci-dessus correspondent à la configuration du dépôt.
La démonstration est prévue sur un réseau privé.

AJOUTER UN CONTENEUR À WEBMON

1. Vérifier que le conteneur tourne sur le même moteur Docker que WebMon.
   Sur la machine qui héberge WebMon :
   docker ps -a

   Il n'a pas besoin d'appartenir au docker-compose de WebMon.
   Un conteneur existant sur cette machine est déjà découvert automatiquement :
   aucune inscription manuelle ni installation d'agent dans le conteneur.

   Les conteneurs sur une autre machine Docker ne sont pas découverts par cette
   installation. Leur service HTTP peut être surveillé comme un site par URL
   avec la procédure ci-dessous.

2. Démarrer le conteneur normalement, avec docker run ou son propre Compose.
   Exemple facultatif : petit serveur HTTP de test, distinct de la stack WebMon.
   Vérifier que le nom webmon-exemple et le port 8082 sont libres.

   docker run -d --name webmon-exemple --restart unless-stopped \
     -p 8082:80 \
     --health-cmd 'wget -q -O /dev/null http://127.0.0.1/' \
     --health-interval 10s --health-timeout 3s --health-retries 3 \
     busybox:1.37 sh -c 'mkdir -p /www; echo OK > /www/index.html; exec httpd -f -p 80 -h /www'

   Le site de test est accessible sur http://IP_DU_SERVEUR:8082/.
   Pour une application existante, garder sa commande et sa configuration ;
   cet exemple n'est pas une étape obligatoire.

3. Attendre un cycle de découverte et la collecte des métriques.
   En général, attendre 30 à 60 secondes, davantage si un cycle est long.
   Actualiser http://IP_DU_SERVEUR/ pour voir le conteneur dans WebMon.
   Ouvrir ensuite :
   http://IP_DU_SERVEUR:3000/d/webmon-containers/webmon-conteneurs

   Le menu Conteneur permet de choisir son nom et de consulter ses sondes,
   son CPU, sa mémoire et son réseau. Les débits nécessitent plusieurs mesures.

4. Vérifier que la sonde représente réellement la santé de l'application.
   WebMon utilise dans cet ordre :
   - Un heartbeat explicitement configuré pour un worker.
   - Le healthcheck Docker natif, s'il existe.
   - Une sonde HTTP découverte sur les ports et chemins connus.
   - Sinon, l'état Docker seul : application Non testé.

   Pour une application sans sonde adaptée, ajouter un healthcheck à son image
   ou à son propre docker-compose.yml, puis recréer ce conteneur.
   Exemple à intégrer à un service HTTP dont l'image dispose de wget :

   healthcheck:
     test: ["CMD-SHELL", "wget -q -O /dev/null http://127.0.0.1:80/health"]
     interval: 10s
     timeout: 3s
     retries: 3
     start_period: 20s

   Adapter le port, le chemin et la commande à l'application.
   /health doit exister : une page d'accueil qui répond ne garantit pas que
   la base de données ou les autres dépendances fonctionnent.
   Pour une base distante, le healthcheck doit vérifier la connexion réelle
   depuis l'application. WebMon ne teste pas cette dépendance automatiquement.

5. Si le conteneur n'apparaît pas ou reste Non testé :
   docker ps -a
   docker logs --tail 50 webmon-monitor
   curl -fsS http://localhost/api/containers

   Vérifier qu'il ne porte pas le label webmon.internal=true, qui masque
   les composants internes. Un conteneur sans HTTP ni healthcheck peut être
   découvert avec ses ressources tout en restant Non testé.

L'ajout à la supervision n'autorise pas automatiquement le redémarrage ou la
reconstruction. La politique par défaut est observe-only (observation).
Configurer séparément config/recovery-policies.json pour autoriser une action.
Le mode de démonstration autorise la reconstruction uniquement du demo-worker.
Guide détaillé : docs/CONTAINER_MONITORING.md

SUPERVISION DES SITES WEB NON CONTENEURISÉS

WebMon peut aussi surveiller des sites HTTP/HTTPS hébergés sans Docker,
sur une autre machine ou sur Internet, s'ils sont accessibles depuis le monitor.

Dashboard : http://localhost:3000/d/webmon-websites/webmon-sites-web
Dans Grafana : Dashboards > WebMon > WebMon - Sites web.
Configuration des URL : config/websites.json
Exemple fourni : config/websites.example.json
Guide détaillé : docs/WEBSITE_MONITORING.md

1. Si la fonctionnalité n'est pas encore déployée, depuis le dossier webmon :
git switch main
git pull --ff-only https://github.com/nicolasqrs/webmon.git main
docker compose -f docker-compose.yml -f docker-compose.demo.yml up -d --build --no-deps webmon-monitor
docker compose -f docker-compose.yml -f docker-compose.demo.yml restart grafana

Sans la démonstration, retirer -f docker-compose.demo.yml des commandes Docker.

2. Ajouter ou modifier les sites depuis le dossier webmon :
nano config/websites.json

Le fichier initial contient []. Exemple de contenu à adapter :
[
  {
    "name": "Mon site",
    "url": "https://www.mon-site.fr/",
    "expected_status": 200,
    "timeout_seconds": 5,
    "failure_threshold": 3
  },
  {
    "name": "Intranet",
    "url": "http://192.168.1.50/health",
    "expected_status": 200,
    "timeout_seconds": 5,
    "failure_threshold": 3
  }
]

3. Enregistrer dans nano : Ctrl+O, Entrée, puis Ctrl+X pour quitter.
Vérifier la syntaxe JSON depuis le monitor :
docker exec webmon-monitor jq empty /website-config/websites.json
Une sortie vide et un code de retour 0 indiquent un JSON valide.

Chaque nom doit être unique. Les modifications sont lues au cycle suivant,
sans redémarrage, et les sites apparaissent automatiquement dans Grafana.
Supprimer une entrée retire sa supervision courante ; son historique reste
dans Prometheus pendant la durée de rétention.

4. Attendre la prochaine sonde et la collecte Prometheus (en général 30 à 60 s),
puis ouvrir le dashboard Sites web indiqué en haut de cette section.
Sélectionner le site dans le filtre pour consulter son résultat et ses courbes.

Pour un site sur la machine Docker, utiliser http://host.docker.internal:PORT/.
Le service doit écouter sur une interface accessible depuis Docker.
localhost dans une URL désigne le conteneur monitor, pas la VM.

Contrôles :
- Requête GET, avec suivi des redirections HTTP/HTTPS (maximum 5).
- Code HTTP final comparé au code attendu (200 par défaut).
- Mesure du temps de réponse.
- Vérification du certificat HTTPS avec les autorités de confiance du monitor.
- Timeout, erreur DNS/TLS ou code inattendu : sonde KO.
- Panne confirmée après plusieurs échecs consécutifs (3 par défaut).
- Un succès remet le compteur d'échecs à zéro.

La boucle attend 30 secondes après chaque cycle. Les sites sont testés
successivement ; des sites lents peuvent allonger cet intervalle.
Cette boucle est indépendante des contrôles et de la récupération Docker.

Le dashboard affiche les sites suivis, les sites OK, les pannes confirmées,
le dernier cycle, les codes HTTP, les temps de réponse et la disponibilité.
La disponibilité est le pourcentage des contrôles enregistrés qui sont OK ;
les interruptions de collecte ne sont pas comptées comme des pannes du site.

Cette version ne redémarre pas les serveurs distants et n'envoie pas de
notifications. CPU et mémoire du serveur distant nécessitent une collecte dédiée.

Vérifier les résultats :
docker logs --tail 50 webmon-monitor
docker exec webmon-monitor cat /runtime/websites.json
curl -fsS http://localhost:9100/metrics | grep '^webmon_website'

Une configuration JSON invalide conserve les derniers résultats.
Si l'âge du dernier cycle augmente, vérifier la configuration et les logs.
Les URL sont présentes dans le fichier d'état local, mais pas dans les labels
Prometheus. Vérifier ce fichier avant de partager son contenu.
